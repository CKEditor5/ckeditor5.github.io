CKEditor 5 changelog

Contribute to this guideShow the table of contents

This is the CKEditor 5 changelog guide. Here you will find information about the most important changes introduced in the release, new features, and bug fixes.

Information about both major and minor breaking changes is available, too, if the release introduces them. You can read more about breaking changes in CKEditor 5 in the Versioning policy guide.

You can find more information about each release in the blog posts linked at the start of each entry.

This guide covers the three latest releases of CKEditor 5. For older releases, see the Previous releases section.

CKEditor 5 v49.1.0 release

Copy link

We are happy to announce the release of CKEditor 5 v49.1.0.

Release highlights

Copy link

⭐ Editing Toolkit

Copy link

We are releasing Editing Toolkit, a new set of APIs for developers who build their own editing experiences.

Editing Toolkit grew out of our work on CKEditor AI, our plug-and-play AI offering. Turn it on, and you have an editor with AI that keeps humans in the loop.

But some teams want to build their own AI integration rather than use a ready-made one. Editing Toolkit gives them the building blocks to work with content in the editor. It consists of two parts:

  • Compare: an editor API that lets you compare two versions of HTML content, then apply or suggest individual changes. You can also preview the changes before they land in the content.
  • Coauthor: think of it as MCP for CKEditor. It lets server-side agents draft content, suggest edits, or leave comments in the editor: through ChatGPT or Claude, or as background jobs. Coauthor is currently in early access, and if you would like to test it, let us know.

Editing Toolkit is not limited to AI. You can also use it in strictly deterministic scenarios like manipulating content with code or comparing it with externally generated HTML, for example, HTML converted from an updated Word file.

⭐ CKEditor AI: custom skills for your features

Copy link

CKEditor AI can now work with the content of your plugins, such as a custom widget or a new HTML element. Upload a custom skill that describes the markup and rules of your feature, then register the plugin with AIEditorConfig#add(). The AI agent then writes and keeps your custom content in the shape your editor accepts, and its proposed changes follow your feature’s rules.

See Registering custom features for details.

⭐ CKEditor AI: hooks for your agent and policies

Copy link

On-premises deployments of CKEditor AI can call a service you host before the agent answers an AI Chat message. With hooks, your service can check each message against your policies, answer from your systems, or pass context and instructions to the CKEditor AI agent. Use them when you already have an AI platform with access to your data and want it to take part in the chat.

⭐ Editor bundle for Cloud Services with your AI coding agent

Copy link

Coauthor runs your editor on the server, so it needs an editor bundle uploaded to Cloud Services. It joins the other features that require the editor bundle. The new ckeditor-bundle skill lets your AI coding agent set it up. It moves the editor into one module that both your application and the bundle use, adds the bundle build for your bundler, checks the bundle with test data, and adds the upload scripts for your CI.

Two new guides come with the skill. Editor bundling with Vite shows how to share one editor definition between your application and the bundle. Testing the editor bundle with test data explains how Cloud Services checks the bundle and how to fix a failed upload.

Other improvements and fixes

Copy link
  • New theme improvements and fixes: v49.0.0 introduced a refreshed default theme built on three layers of design tokens (foundation scales, semantic roles, and per-component tokens), with legacy variable names kept as aliases. Some aliases were silently ignored even though the migration guide said they worked. They work again, so overrides of focus borders and the shadows of dropdowns, balloons, menus, and comment and suggestion cards apply with no changes on your side. Additionally, more of the UI moved from hard-coded values to tokens (#20255, #20257, #20259): button colors in the resting, hover, and active states, toolbar button borders and radius, form and dialog headers, the insert table grid, and find and replace results. Every new token defaults to the value used today, so the default theme looks the same. See the full token list in the theme customization guide.
  • Shadow DOM support for more features: the CKBox file manager and image editor, the “Edit source” dialog of enhanced source editing, and footnotes work correctly when the editor renders in a shadow root. Plugin authors get two helpers for events that do not cross a shadow boundary, such as scroll: listenToEventRoots() listens on the document and on every shadow root the editor lives in, and DomTargetsListener listens on a set of targets you can refresh, like a balloon’s positioning target. See the Shadow DOM deep dive.
  • More reliable balloons and toolbars: tooltips, the link balloon, and the mention list appear in the right place again on scrolled pages when <body> or the overlay container is positioned (a v49.0.0 regression, #20251).
  • Content loading: some browsers started parsing <?target data?> markup as processing instruction nodes instead of comments, which made the editor throw while loading or pasting such content. The editor ignores these nodes the same way it ignores comments, and data processors have a new skipProcessingInstructions flag for integrations that need to keep them.
  • Email export fixes: Email export converts hsl() and hsla() colors to rgb() and rgba() through the new transformEmailStylesColors() transformation, since many email clients, including Outlook, do not support HSL. The default font and table palettes also no longer trigger warnings in the email configuration logger.

MINOR BREAKING CHANGES

Copy link

  • collaboration-core, comments: Focused comments and suggestions are now marked with a focus ring instead of a background color. The --ck-comment-focus-background-color and --ck-suggestion-box-focus-background-color CSS variables have been removed. To style the focus ring, use the new --ck-comment-focus-border-color, --ck-comment-focus-shadow, --ck-suggestion-box-focus-border-color, and --ck-suggestion-box-focus-shadow CSS variables.

  • ai: The AIEditorConfig type describing the editor configuration snapshot has been renamed to AIEditorConfigSnapshot. The AIEditorConfig name now refers to the new plugin that produces the snapshot and registers custom features. If you used the AIEditorConfig type (for example, to type DocumentCompareSnapshot#editorConfig or AIEditingDocumentData#editorConfig), replace it with AIEditorConfigSnapshot.

  • comments: The default CommentThreadView no longer renders the comment thread header, and the BaseCommentThreadView#commentThreadHeaderView property is deprecated. Customizations of the header, such as buttons added to it or styles for the .ck-thread__header and .ck-context CSS classes, no longer apply. The reopen button is now available in the first comment as CommentThreadView#reopenButton. If you need the header, add commentThreadHeaderView to the template of your custom comment thread view.

  • comments: The --ck-comment-input-padding CSS variable now sets only the padding of the comment field container, not the padding inside the comment field. If you used it to change the padding inside the comment field, use the new --ck-comment-input-field-padding CSS variable instead.

  • revision-history: Some Revision History CSS variables now style different parts of the refreshed sidebar:

    • --ck-revision-history-sidebar-revision-vertical-spacing sets only the spacing between revisions. Use the new --ck-revision-history-sidebar-time-period-vertical-spacing for the spacing between the time period groups.
    • --ck-revision-history-revision-border-color sets the whole card border. --ck-revision-history-revision-selected-border-color and --ck-revision-history-revision-highlighted-border-color set the vertical line that marks the selected and the compared revisions.
    • The time period labels no longer use the inverse text color. If you changed their background with --ck-revision-history-sidebar-period-background-color, set their text color with the new --ck-revision-history-sidebar-period-text-color.
    • --ck-revision-history-revision-highlighted-hover-background-color no longer has an effect, because the actions button of a compared revision uses the default button hover background.

  • utils: The DOM event passed to the listenToShadowRoots() callback is now typed after the event option, the same way as in DomEmitter#listenTo(), instead of any. A TypeScript callback that declares a narrower DOM event type than the one of the event it listens to no longer compiles. Declare the matching DOM event type, or narrow it inside the callback.

Features

Copy link

  • document-outline, footnotes, merge-fields, pagination, real-time-collaboration, revision-history, slash-command, source-editing-enhanced, template, uploadcare: The document outline, table of contents, footnotes, revision history, merge fields, Uploadcare, pagination, presence list, templates, and slash command features expose new CSS custom properties for their colors, sizes, and spacing, and several of their defaults now follow the semantic theme roles. Every new property defaults to the current value, so the default theme renders unchanged.

    • Document outline: the active item follows the semantic accent text color (--ck-color-text-accent), and the hover text color has a new name (--ck-document-outline-item-hover-text-color). The legacy --ck-document-outline-item-hover-state-color keeps working.
    • Table of contents and footnotes: the widget label text color (--ck-table-of-contents-label-text-color, --ck-footnotes-widget-label-text-color). The label backgrounds follow the semantic secondary text color, and the table of contents background follows the subtle surface (--ck-color-surface-subtle).
    • Revision history: the selected revision border follows the semantic accent border color (--ck-color-border-accent), and the actions button of the selected revision has its own text color at rest and on hover (--ck-revision-history-revision-selected-actions-text-color, --ck-revision-history-revision-selected-actions-hover-text-color).
    • Merge fields: component-first names for the colors (--ck-merge-fields-outline-color, --ck-merge-fields-value-outline-color, --ck-merge-fields-with-warning-outline-color, --ck-merge-fields-block-outline-color, --ck-merge-fields-affix-text-color, --ck-merge-fields-form-error-background-color), the label and preview badge backgrounds (--ck-merge-fields-label-background-color, --ck-merge-fields-preview-badge-background-color), and the affix font (--ck-merge-fields-affix-font-family). The legacy --ck-color-merge-fields-* names keep working.
    • Uploadcare: the widget font size, font family, radius, padding, text and border colors (--ck-uploadcare-font-size, --ck-uploadcare-font-family, --ck-uploadcare-border-radius, --ck-uploadcare-padding, --ck-uploadcare-text-color, --ck-uploadcare-secondary-text-color, --ck-uploadcare-muted-text-color, --ck-uploadcare-border-color), and suffix-convention names for the form colors (--ck-uploadcare-form-image-background-color, --ck-uploadcare-form-error-icon-color, --ck-uploadcare-form-skeleton-background-color). The legacy --ck-uploadcare-color-* names keep working. The widget font now follows the editor UI font (--ck-font-family), so overriding the editor font also changes the Uploadcare widget.
    • Pagination: the page number label text color (--ck-pagination-label-text-color).
    • Presence list: the avatar border and users counter colors (--ck-presence-list-avatar-border-color, --ck-presence-list-counter-border-color, --ck-presence-list-counter-background-color, --ck-presence-list-counter-text-color) can now be set on :root (or :host in a shadow root). The avatar border follows the subtle surface. These properties are now override points only: because the counter colors depend on the avatar color of each user, their defaults are applied where they are used, so reading them with var() in your own CSS returns nothing unless you set them.
    • Templates: the description text color (--ck-template-description-text-color). The template title and description now follow the button text color.
    • Slash command: the icon chip text color, background, and radius (--ck-slash-command-icon-text-color, --ck-slash-command-icon-background-color, --ck-slash-command-icon-border-radius).

  • basic-styles, block-quote, code-block, horizontal-line, image, list, mention, page-break, table: The block quote border, code block, inline code, horizontal line, page break, table borders and header, and to-do list checkmarks in the content expose --ck-content-* CSS custom properties, so the content rendered inside .ck-content can be restyled on :root (or :host in a shadow root) without overriding element rules. Every new property defaults to the current value, so the default theme renders unchanged. The table caption, image caption, and mention color properties were renamed to follow the current naming convention (for example --ck-content-table-caption-background-color), and the former --ck-content-color-* names keep working as fallbacks on :root (or :host in a shadow root) and in scoped selectors. Closes #20253.

  • ckbox, fullscreen, html-embed, html-support, media-embed, style, ui, widget: New semantic color roles cover design intents that had no shared token, so they can be restyled once on :root (or :host in a shadow root) instead of per component. The components that read the new roles keep their current colors, so the default theme renders unchanged. Closes #20259.

    • --ck-color-surface-subtle: a muted panel or placeholder surface. The fullscreen layout, HTML embed, HTML object embed, media embed placeholder, and the disabled style in the style grid now read it instead of the foundation --ck-color-base-foreground.
    • --ck-color-border-subtle: a light border. The blurred widget outline now reads it.
    • --ck-color-surface-overlay: the scrim behind modal dialogs, read by --ck-dialog-overlay-background-color.
    • --ck-color-surface-skeleton and --ck-color-surface-skeleton-highlight: the loading shimmer, read by the CKBox image processing placeholder.
    • --ck-color-interactive-disabled-surface: the background of a disabled input.
    • --ck-color-text-placeholder: the editing area placeholder text, read through --ck-color-engine-placeholder-text.
    • --ck-color-feedback-error-surface, --ck-color-feedback-success-surface, and --ck-color-feedback-warning-surface: light, translucent backgrounds for messages and fields in a feedback state, available for custom components (no built-in component reads them yet).

    The focus border color (--ck-focus-border-color) now derives from --ck-color-base-focus, so changing the foundation focus color also moves the focus border. The labeled field and labeled input error text now read --ck-color-text-error. Both resolve to the same values as before.

  • code-block, find-and-replace, heading, style, table, ui: Toolbars, form and dialog headers, dropdowns, split buttons, lists, tab buttons, the insert table grid, the heading dropdown, find and replace, code blocks, and the style grid expose new CSS custom properties that can be restyled on :root (or :host in a shadow root). Every new property defaults to the current value, so the default theme renders unchanged. Closes #20257.

    • Toolbar: the border and radius of the toolbar’s own buttons in every toolbar (--ck-toolbar-button-border, --ck-toolbar-button-border-radius), including compact toolbars, toolbars in dropdown panels, and open dropdown and split buttons in toolbars, and the separator width (--ck-toolbar-separator-width). The button tokens do not reach lists in dropdown panels.
    • Form header and dialog header: the background and the text color of the label, the header icon, and the header buttons, such as the dialog close button (--ck-form-header-background, --ck-form-header-text-color, --ck-dialog-header-background).
    • Dropdown: the gap between the label and the arrow (--ck-dropdown-arrow-gap). The open dropdown button radius (--ck-dropdown-panel-uniform-button-border-radius) now defaults to --ck-button-border-radius.
    • Split button and list: the separator width and height (--ck-split-button-separator-width, --ck-list-separator-height).
    • List item button: the text color and hover background of a toggleable item in the “on” state (--ck-list-item-button-on-text-color, --ck-list-item-button-on-hover-background).
    • Tab button: the focus border color and the label color of the active tab (--ck-tab-button-focus-border-color, --ck-tab-button-active-text-color).
    • Insert table grid: the cell border, and the background and border of selected cells and of the cell under the pointer (--ck-insert-table-dropdown-box-border-color, --ck-insert-table-dropdown-box-on-background, --ck-insert-table-dropdown-box-on-border-color, --ck-insert-table-dropdown-box-hover-background, --ck-insert-table-dropdown-box-hover-border-color).
    • Heading dropdown: the label width and the list item minimum width (--ck-heading-dropdown-label-width, --ck-heading-dropdown-list-item-min-width).
    • Find and replace: the result and selected result background and text color (--ck-find-result-background, --ck-find-result-text-color, --ck-find-result-selected-background, --ck-find-result-selected-text-color). The legacy --ck-color-find-result-selected keeps working.
    • Code block: the language label background and text color (--ck-code-block-label-background, --ck-code-block-label-text-color). The legacy --ck-color-code-block-label-background keeps working.
    • Style grid: the border of the selected style and of the selected style under the pointer (--ck-style-panel-button-on-border-color, --ck-style-panel-button-on-hover-border-color).

  • ai, collaboration-core, comments, real-time-collaboration: The user marker tooltip text color and the background around the comment reply field are now themable through --ck-user-marker-tooltip-text-color and --ck-comment-input-container-background-color, and the border of format suggestions in the sidebar follows the semantic --ck-color-border-accent role. The AI tabs overlay follows the dialog layer (--ck-layer-dialog), so it stays right below dialogs when that layer changes.

  • collaboration-core, comments, revision-history: The suggestion and comment markers, the annotation type bar, pills, user avatars, and the confirmation view expose new CSS custom properties for their line width and style, colors, and sizes. Because it is built on design tokens, matching the editor to your product means overriding a few tokens, and those overrides keep working across editor updates.

The refresh also changes content styles, so published documents look slightly different. Block quotes, code blocks, and horizontal lines use lighter colors, and comment and suggestion markers use new ones.

The new look applies automatically when you upgrade. To keep the previous look, load the legacy theme preset after the editor styles and use the content styles rollback snippets for published content.

Design tokens for theme customization

Copy link

The theme now uses three layers of design tokens instead of a flat set of CSS variables (#19910): foundation scales (spacing, radius, color, typography), semantic roles shared across components, and per-component tokens. Override a few foundation tokens to align the editor with your design system, one semantic token to restyle a whole class of controls, or a component token such as --ck-button-border-radius to change one component without side effects.

Overrides of legacy variable names keep working. CSS that reads legacy names, such as var(--ck-spacing-small), needs the opt-in aliases. Scoped overrides of foundation tokens no longer reach components, so override the component token for per-element changes. See the theme token naming guide, the theme customization guide, and the refreshed theme and design tokens section of the update guide.

⭐ Redesigned AI Review and more unified AI experience

Copy link

AI Review has a new design and a Suggest action, which adds an AI change as a Track Changes suggestion instead of applying it directly. While you work through the changes, a balloon in the content follows the current one and a progress bar shows how many are left. AI Review, AI Quick Actions, and Proposed Changes in AI Chat now share the same cards and controls, so actions sit in similar places in all three.

The whole AI interface, including AI Chat, AI Review, Quick Actions, and AI Translate, now uses the refreshed theme and responds to the same token overrides as the rest of the editor. If you customized the AI interface, update your overrides, because legacy AI token names have no fallback. See the AI package section of the theme migration guide for the name mappings.

Trusted Types support

Copy link

CKEditor 5 now works in applications that enforce Trusted Types with the require-trusted-types-for 'script' Content Security Policy directive (#10845). Before, the browser blocked the HTML strings the editor inserts into the page, so the editor could not run at all. Every place where the editor inserts HTML, including in premium features, now goes through a Trusted Types policy named ckeditor5.

The policy does not sanitize content, so validating the data you load into the editor remains your responsibility. See the Trusted Types section of the CSP guide and the API docs for trustedHtml().

Error handling without the Watchdog

Copy link

The Watchdog has been removed (along with the @ckeditor/ckeditor5-watchdog package), so CKEditor 5 no longer restarts the editor after an unhandled error. The editor keeps running with its content and undo history, but its state may be inconsistent, so your application decides what to do next: reload the editor, notify the user, or report the error. Register a callback with the new onEditorError() function to learn about errors and which editor or context caused them.

See the Error handling guide and the Migrating from the Watchdog guide for integration and migration instructions.
