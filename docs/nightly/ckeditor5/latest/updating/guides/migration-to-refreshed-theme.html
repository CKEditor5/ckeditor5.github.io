Migrating to the refreshed theme

Contribute to this guideShow the table of contents

Two things changed at once, and it helps to keep them separate:

  1. A new token architecture – the --ck-* CSS custom properties were reorganized into three layers (foundation → semantic → component). This reorganization is value-neutral: on its own it changes no pixels.
  2. A refreshed default theme – new color, spacing, radius, elevation, and font values layered on that architecture, for a more modern default look.

Most “will my customization break?” questions are about #1 (names/overrides). Most “why does it look different?” questions are about #2 (values). We call those out separately throughout.

There is also one structural change that affects where you override tokens: every token is now declared on :root, :host (not just :root), so the theme resolves inside a shadow root too. See Shadow DOM.

Benefits of the new token architecture

Copy link

The editor UI uses one set of design tokens in three layers. The foundation layer holds the raw values, the semantic layer gives them shared design roles, and the component layer exposes them as override points for individual components. Each value is defined once and flows up through the layers:

:root,
:host {
	/* Foundation - the raw value and a scale step derived from it. */
	--ck-radius-base: 8px;
	--ck-radius-md: calc(var(--ck-radius-base) / 2);

	/* Semantic - the shared design role. */
	--ck-border-radius-control: var(--ck-radius-md);

	/* Component - the per-component override point. */
	--ck-input-border-radius: var(--ck-border-radius-control);
}
Copy code

Change a value at the layer that matches its reach:

  • Foundation – override --ck-radius-base to resize the whole radius scale. If you still set the legacy --ck-border-radius, the scale derives from it instead, so --ck-radius-base has no effect.
  • Semantic – override --ck-border-radius-control to round controls such as buttons and inputs.
  • Component – override --ck-input-border-radius to round only inputs.

Set foundation and semantic overrides on :root (or on the shadow host when the editor runs in a shadow root). A foundation or semantic override on a narrower selector usually does not reach the component tokens. The theme derives each layer from the one below it on :root, so the component tokens inherit values already computed there. To restyle a single element, override its component token instead. The Theme token naming guide describes the layers in detail, and the Theme customization guide explains global and scoped overrides.

Colors follow the same model. Surface, text, and interactive colors are semantic roles, so a theme variant, for example a dark or high-contrast palette, is a set of token overrides rather than per-component CSS. See the dark theme example for a complete variant. Token names follow a documented convention, which makes them straightforward to map to variables in design tools such as Figma.

Token names do not encode their values, so future theme updates can change the default values without renaming the tokens. Custom plugins that build on the same semantic tokens follow your overrides and stay visually consistent with the editor. Overrides of the old token names still work, with a few exceptions. See The two compatibility mechanisms.

Do I need to do anything?

It depends on how your integration uses and customizes the editor. Find the rows that describe your setup in the table below and follow the linked sections. If several rows apply, go through each of them.

The two compatibility mechanisms

Copy link

Old token names keep working through two independent mechanisms. Which one applies depends on whether you override a token (set its value) or read it (use it in your own CSS).

Overriding old token names

Copy link

If you set a legacy token name to re-skin the editor, it usually still works, and you need no changes. Check the exceptions:

  • Some names work only on :root – see Overriding on a narrower selector.
  • Some names no longer work or reach only part of the UI – see Legacy names to replace and Focus styles.
/* The way you re-skinned the editor on the old theme - still works as-is. */
:root {
  --ck-color-toolbar-background: #1e1e1e;
  --ck-color-button-on-background: #0a84ff;
}
Copy code

Under the hood, each place the theme uses a token reads the old name first, then falls back to the new one:

/* Inside the theme (you don't write this - it's why your override wins): */
property: var(--ck-old-token, var(--ck-new-token));
Copy code

Because the old name is read at each point of use, an override works on any selector, not only :root – set it on a wrapper (for example .ck-sidebar) and it applies to the editor UI inside. A few re-themed tokens are the exception; see Overriding on a narrower selector.

Some renamed tokens use the reverse order. The theme still declares the old name with its default value, so the new name is read first and has no value until you set it:

/* Inside the theme: the new name is empty unless you set it, so the old name keeps working. */
property: var(--ck-new-token, var(--ck-old-token));
Copy code

An override of the old name still works on any selector. If you set both names, the new one wins. The renamed tokens are listed in Feature tokens.

Warning

Without !important, your override must load after the editor CSS (same :root specificity – last one wins).

Prefer the new names going forward. The legacy names are a compatibility layer, not a permanent API – in new or updated overrides, use the new names (Token name reference). See Your existing custom styles.

Reading old token names

Copy link

If your own CSS reads a legacy token name, add the opt-in aliases below to your own styles so those names resolve.

.my-widget { padding: var(--ck-spacing-small); }   /* your CSS reads an old name */
Copy code

Copy the aliases block below into your stylesheet. Without them, var(--ck-spacing-small) resolves to nothing; with them, to the new value (--ck-spacing-sm).

When to use it: only to read old names in your CSS.
When not to: it does not help with overriding – that already works without it (Overriding old token names). If you do not read old names, pasting it just adds unused definitions.

Mind the order – it can undo your own overrides. The aliases (re)declare the old names on :root. If they come after a place where you override an old name, they reset it back to the new value and your override is lost:

:root { --ck-spacing-small: 20px; }   /* your override… */
/* …then the aliases below re-declare --ck-spacing-small → your 20px is gone */
Copy code

Save the aliases block below as your own file and load it between the editor CSS and your overrides – then reads resolve and your overrides keep winning:

<link rel="stylesheet" href=".../ckeditor5.css">	<!-- 1. editor -->
<link rel="stylesheet" href="legacy-aliases.css">	<!-- 2. the aliases snippet, saved as your own file -->
<link rel="stylesheet" href="my-overrides.css">		<!-- 3. your overrides -->

Override-only tokens

Copy link

A handful of tokens that components re-theme internally keep working as overrides, but are not in the opt-in legacy aliases, so reading them resolves to nothing. Read their new name instead.

:root { --ck-color-button-on-background: lime; }			  /* ✅ override still re-skins */
.mine { background: var(--ck-color-button-on-background); }   /* ❌ empty (override-only) */
.mine { background: var(--ck-button-on-background-color); }   /* ✅ read the new name */
Copy code

Override-only tokens (set works, read does not – read the new name):

Many newer component tokens work the same way. The theme declares them initial and applies their default where they are used, so an override reaches the component, but reading them in your own CSS resolves to nothing unless you set them. Examples are the button text colors (--ck-button-default-text-color and its hover and active variants), the list item button states (--ck-list-item-button-text-color, --ck-list-item-button-open-background), the find and replace result colors (--ck-find-result-background), and the presence list colors (--ck-presence-list-counter-background-color). To use such a color in your own component, read the token it falls back to, usually a semantic role such as --ck-color-text-primary or --ck-color-interactive-hover-surface.

The border shorthands of inputs, dropdown panels, balloon panels, toolbars, and autocomplete results (--ck-input-border, --ck-dropdown-panel-border, --ck-balloon-panel-border, --ck-toolbar-border, and --ck-autocomplete-results-border) are override-only too. The theme composes them where they are used, so a border color set on any selector, under its old or new name, reaches the border. To read the border color, read the color token of the component, such as --ck-input-border-color or --ck-dropdown-panel-border-color, which also keeps an override of that token.

The split button tokens are override-only under both names. The theme does not declare the legacy --ck-color-split-button-hover-background and --ck-color-split-button-hover-border on :root, and the new names are declared initial, so you can override them but not read them. The legacy hover border colors only the separator of a hovered split button. The focused separator follows the focus color. The new --ck-split-button-focus-border-color lets you set the focused separator separately. To move a legacy override to the new names:

:root {
	--ck-split-button-hover-background: hsl(0, 0%, 95%);	/* was --ck-color-split-button-hover-background */
	--ck-split-button-hover-border-color: hsl(0, 0%, 60%);	/* was --ck-color-split-button-hover-border */
}
Copy code

The inner start border of the split button arrow, next to the action button, has its own width, --ck-split-button-arrow-border-inline-start-width, which follows --ck-button-border-width. If you set another border width only through the --ck-button-border or --ck-toolbar-button-border shorthand, set this token to the same width as well, or to 0 to avoid a doubled line between outlined buttons.

Z-index layers

Copy link

The old z-index names keep working both ways. The default theme still declares them, so you can read them without the opt-in aliases. The editor also reads them first, so overriding them on :root (or :host in a shadow root) still works. On a narrower selector, they reach only part of the UI; see Overriding on a narrower selector.

One thing changed: the panel layer no longer derives from --ck-z-default. In the previous theme, overriding --ck-z-default also moved panels, such as menus and the sticky toolbar, by the same amount. Now it moves only the base layer. To shift the base and panel layers at once, override --ck-z-base:

:root { --ck-z-panel: 5000; }	/* ✅ moves the panel layer */
:root { --ck-z-default: 100; }	/* moves only the base layer now */
:root { --ck-z-base: 100; }		/* ✅ moves the base and panel layers, as --ck-z-default used to */
Copy code

Dialogs do not move with --ck-z-base. They follow --ck-layer-dialog, which derives from the constant --ck-z-modal (9999), and so do the tooltips. The UI layered next to dialogs follows the same layer: the mention list, the emoji picker, and CKBox shown above them, and the AI tabs overlay right below them. To raise them together, override --ck-layer-dialog, --ck-z-dialog, or --ck-z-modal on :root:

  • The button state colors from the override-only table above.
  • The thread header colors.
  • --ck-color-focus-border in buttons, inputs, the editing area, and menu bar items.

:root { --ck-border-radius: 6px; }			/* panels and dialogs: 6px, buttons and inputs: 3px */

Legacy names to replace

Copy link

A few legacy names no longer work, or work only in part of the UI, because their style was redesigned. Use the replacements below instead:

Focus styles

Copy link

The legacy --ck-color-focus-border is now called --ck-focus-border-color. Overriding either name on :root changes the focus color in the whole editor UI.

Buttons, inputs, the editing area, and menu bar items now change only their border color on focus, so a custom border width stays the same. That is why they no longer read --ck-focus-ring, which sets the whole border: width, style, and color.

Other elements, such as focused image captions, still read --ck-focus-ring. Switch buttons, comment threads, and the source editing area, follow only a :root override of --ck-focus-ring.

To change the focus border color of the particular elements, use the following tokens:

For example, an override that hid the focus border of the editing area in the previous theme needs the new token now:

.ck.ck-editor__editable { --ck-focus-ring: none; }									/* ❌ no effect now */
.ck.ck-editor__editable { --ck-editor-editable-focus-border-color: transparent; }	/* ✅ hides the focus border */
Copy code

In the default theme, --ck-color-focus-border-coordinates no longer sets the focus color. It now colors only the pulse around the buttons that insert a paragraph next to a widget. To change the focus color, override --ck-focus-border-color or the legacy --ck-color-focus-border.

Rounding the editor’s outer shell

Copy link

The editor’s outer frame – the toolbar area and the editing area that together form the editor box – now rounds from a single token, --ck-editor-outer-radius. The frame and sticky-panel radii derive from it inside the .ck-rounded-corners scope that every editor UI carries. That scope re-defines these tokens on the element itself, so a :root override of any of them is shadowed and does nothing, including an override of --ck-editor-outer-radius. Set --ck-editor-outer-radius on .ck-rounded-corners instead, and load your CSS after the editor CSS:

:root { --ck-editor-outer-radius: 12px; }				/* ❌ no effect - shadowed on .ck-rounded-corners */
:root { --ck-editor-frame-border-radius: 12px; }		/* ❌ no effect - same reason */
.ck-rounded-corners { --ck-editor-outer-radius: 12px; }	/* ✅ rounds the whole editor shell */
Copy code

The legacy --ck-rounded-corners-radius hook still works and takes precedence over the default, so an integration that already set it keeps working; otherwise the default comes from --ck-border-radius through --ck-radius-corners.

The editor top no longer reads --ck-sticky-panel-uniform-border-radius. That token still controls non-editor sticky panels, but the editor chrome follows --ck-editor-outer-radius. The sticky toolbar is flat (square top) by default; opt into a radius for the stuck state with --ck-editor-sticky-panel-outer-radius.

Only the editor’s own top-level editing roots round this way. Secondary editables that share the .ck-editor__editable class – comment inputs, the AI and revision-history sub-editors, and nested editables such as image captions and table cells – are intentionally left unrounded.

Your existing custom styles

Copy link

Whatever you used to customize the editor – raw .ck-* selectors, token overrides, higher-specificity rules, or a mix – it keeps working. But applying is not the same as fitting: the new theme ships different default values (colors, spacing, radius). Overrides whose values were chosen to harmonize with the old defaults still take effect, but may no longer match the surrounding new values – e.g. a border color picked to contrast the old toolbar background now sits next to a different one, so the contrast you tuned for is off.

The recommended approach has two steps:

  1. First, see the editor on the new theme with no changes. The refreshed defaults may already do what some of your overrides did – you may be able to drop a few.
  2. To keep your look, start from the old baseline: load the legacy theme preset, then your custom CSS on top – see Keep your custom design on top of the preset.

Your customizations resolve this way: raw selectors win by the cascade (markup and class names are unchanged, so they still match), token overrides win through the bridges (The two compatibility mechanisms), and a mix composes by those rules – for same-specificity token overrides, load your CSS after the editor CSS. (!important also forces an override regardless of load order, but reach for it only when you cannot control the order – it is harder to override afterwards and tends to escalate.)

/* A typical mixed stylesheet - all of this still applies. */
.ck.ck-toolbar { border-bottom: 2px solid var(--brand); }	/* raw selector → cascade */
:root { --ck-color-button-on-background: var(--brand); }	/* old token → bridge */

Shadow DOM

Copy link

Every token is now declared on :root, :host, so the theme resolves inside a shadow root. If your editor is mounted in a shadow root, a :root override has no effect on it. The tokens still inherit into the shadow root, but the editor declares them again on :host, and that declaration wins. Override the tokens on the shadow host element instead, for example with a class that you put on it. A rule in the main document that matches the host is enough:

/* Light DOM */  :root				  { --ck-color-toolbar-background: #1e1e1e; }
/* Shadow DOM */ .my-editor-shadow-host { --ck-color-toolbar-background: #1e1e1e; }

Published content

The refreshed theme also changed a few content colors – block quotes, code blocks, horizontal lines, and comment/suggestion markers. Because .ck-content styles apply to already-published documents, your existing content now renders with the new colors.

If you already use the legacy theme preset, these same content rollbacks are included in it (Keeping the old look) – it carries .ck-content rules, not just editor-UI tokens. Token name reference

Copy link

This section maps each legacy name to its new name. You rarely need it, because overriding old names keeps working (Overriding old token names). It matters when you want to adopt the new names or to read a token in your own CSS. The foundation tokens are listed in full below, and the color tokens follow one pattern (see Component colors).

Reading an old name works with the opt-in aliases snippet, except for the override-only names listed in Override-only tokens. Reading those resolves to nothing, so read the new name instead. The feature tokens are the reverse: the new name has no value by default, so read it with the old name as its fallback. The old z-index names keep their read aliases in the default theme, so they need no snippet (see Z-index layers).

Foundation

Copy link

To scale all editor spacing at once, override --ck-spacing-unit. It is still the anchor of the spacing scale, both in the refreshed theme and in the legacy theme preset.

To place your own UI relative to dialogs, read --ck-layer-dialog rather than --ck-z-modal, for example z-index: calc(var(--ck-layer-dialog) + 1). An override of the dialog layer then moves your UI too (see Z-index layers).

Note

Comment and suggestion cards no longer have the active shadow, so overriding --ck-shadow-lg does not bring it back. See Legacy names to replace.

Feature tokens

Copy link

Some content and feature tokens were renamed to the current naming convention. These renames use the reverse fallback order: the theme reads the new name first, and the new name has no value until you set it (see Overriding old token names). Overriding either name works. To read the value in your own CSS, read both names in the same order, so an override of either one applies, for example var(--ck-content-mention-text-color, var(--ck-content-color-mention-text)).

Consolidated

Copy link

The old track changes and suggestion colors (--ck-color-suggestion-marker-*, -widget-*, and -box-*) were consolidated into the shared --ck-color-diff-* semantic layer. It covers deletion, insertion, and format changes for backgrounds, borders, strokes, widgets, and boxes. Overriding the old names still works (Overriding old token names). You can also recolor at two levels: the shared --ck-color-diff-* tokens change all diffs at once, and the per-surface --ck-suggestion-marker-*-color, -box-*, and -widget-* tokens change one surface:

/* Recolor all insertions at once via the shared diff layer. */
:root { --ck-color-diff-insertion-border: hsl(157 80% 34% / 50%); }
