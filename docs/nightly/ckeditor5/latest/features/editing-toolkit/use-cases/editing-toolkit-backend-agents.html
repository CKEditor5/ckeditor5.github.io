Editing Toolkit with backend agent workflows

Show the table of contents

Backend agent workflows process documents on the server. For example, one agent updates a document and a second agent checks the result. With Coauthor, agents read and edit the document without anyone having it open in a browser. Their changes arrive as Track Changes suggestions that people review.

Available in early access

Contact us to enable Coauthor in your trial or existing environment. We will help you with the server-side setup.

Contact us View plans

Video

Copy link

In the video, a backend job runs two agents over several documents. The second agent checks the work of the first one, and a person reviews their suggestions.

When to use this approach

Copy link
  • Many documents can be drafted or processed by agents before any user opens them, for example after a new regulation or a product rename.
  • Review steps can be done by agents, which leave comments on what a person should check.
  • People keep editing the documents while the job runs, and they should decide on every change later.

If a job rewrites the document HTML itself, it can overwrite what a colleague typed in the meantime, drop markup that the editor needs, and leave no trace of who changed what. Coauthor checks each edit against your editor, and each suggestion can carry the name of the agent that made it.

How it works

Copy link

  1. A trigger starts the job in your backend, such as a change notice from your legal team.

  2. For each document and each agent, your backend opens a Coauthor session on the document. It names the agent as the actor of the session and sets suggest mode, so that every edit becomes a suggestion.

  3. Your backend starts the agent with a session token that works for this session only. The agent works with its own prompt, such as the change notice or the full regulation.

  4. The agent reads and edits the document with Coauthor’s MCP tools. Coauthor checks each edit against your editor and explains what it refuses.

  5. With applyOn: "everyWrite", each accepted edit reaches the document at once. Coauthor applies it with Compare inside the server-side editor, and the suggestion reaches everyone who has the document open through real-time collaboration, under the agent’s name.

  6. When the agent is done, your backend closes its session and opens one for the next agent.

  7. The next agent, such as a review agent, reads the document with the earlier suggestions in it, and fixes what the first agent missed.

  8. Its suggestions reach the document in the same way.

  9. Later, people open the document and accept or reject each suggestion. Tell them that suggestions wait for them, for example in your application’s inbox.

Your backend sets suggest mode. A token signed for suggest mode allows nothing else, so the agent cannot switch to direct edits.

Without real-time collaboration, your backend sends the document when it opens the session, as an uploaded document, and gets the changed document back, with the suggestions in it, to save in your system.

What you need

Copy link
  • Access to Coauthor, which is in early access. Your Cloud Services environment needs an editor bundle with the same plugins as your editor, including DocumentCompare and Track Changes. See Coauthor setup.
  • A backend that signs tokens with an access key of your environment and runs your agents with an MCP client.
  • The Track Changes integration in your editor, so that people can review the suggestions. The editor needs no DocumentCompare or ProposedChanges for this approach.
  • For live documents, real-time collaboration. Without it, your own storage for the documents.
